Equivalent Time Scales

Many things age on more than one clock at once. A gas turbine runs for hours, and it is also started and stopped; every start heats and cools the hot parts, and wears them as many hours of steady running would. A pump runs for hours and is cycled; an aircraft flies hours and makes landings; a vehicle covers kilometres and runs engine hours. Which clock should a life be measured on?

Often neither alone. Two machines with the same running hours are not equally worn if one was started ten times as often. An equivalent time scale combines the clocks into one age,

\[T = h + k\,s ,\]

with \(h\) the hours, \(s\) the starts and \(k\) what one start is worth in hours. Gas-turbine makers call \(T\) the equivalent operating hours and quote a fixed \(k\) (one start counts as some number of hours). Equivalence(Weibull) learns \(k\) from your failure data, together with the life distribution on \(T\), so you can tell how much a start really costs your fleet, with a confidence interval, and test whether starts matter at all. The statistics literature calls the best such combination the ideal time scale (Kordonsky and Gertsbakh, 1993; Duchesne and Lawless, 2000).

The API reference is Equivalent Time Scales.

Where the information about k comes from

\(k\) is learned by comparing units that use the two clocks at different rates. If a peaking unit (many starts per hour) fails after fewer hours than a base-load unit (few starts per hour), the difference is what the starts cost. If every unit made the same number of starts per hour, there would be nothing to compare: \(h + k s\) would be the hours times the same factor for every unit, and that factor cannot be told apart from the life distribution’s scale. The fit refuses such data and says so.

A worked example: starts on a fleet of turbines

240 units run in three duties: base load (about one start per 100 hours), cycling (one per 20 hours) and peaking (about one start every three hours). Each has been followed for between 5,000 and 25,000 hours; 40% have had the failure being studied, the rest are still running. The data are simulated, so the truth is known: one start is worth 20 hours, and the life on the combined clock is Weibull with scale 30,000 equivalent hours and shape 2.5.

import numpy as np
import pandas as pd
import surpyval as sp

rng = np.random.default_rng(42)
n = 240
duty = rng.choice(["base load", "cycling", "peaking"], n, p=[0.4, 0.35, 0.25])
rate = pd.Series(duty).map(
    {"base load": 0.01, "cycling": 0.05, "peaking": 0.3}
).to_numpy()
life_in_hours = 30000 * rng.weibull(2.5, n) / (1 + 20 * rate)
followed = rng.uniform(5000, 25000, n)
failed = life_in_hours < followed
hours = np.where(failed, life_in_hours, followed)
df = pd.DataFrame(
    {
        "hours": hours.round(0),
        "starts": np.round(rate * hours),
        "c": np.where(failed, 0, 1),
        "duty": duty,
    }
)
df.head()

Each row is one unit: its hours and starts at its failure (c = 0) or now, if it is still running (c = 1). This is ordinary univariate data on the main clock, hours (x_col, c_col), with the second clock, starts, read at the same moments (x2_col). The censoring is the unit’s: the starts have none of their own. Fit the combined clock; \(k\) is measured in the main clock’s units.

model = sp.WeibullEquivalence.fit_from_df(
    df, x_col="hours", x2_col="starts", c_col="c"
)

How to read it:

  • k = 18.4: one start is worth about 18 hours of running (the truth is 20). The 95% confidence interval, 14.2 to 23.7 hours, is the range of values the data are consistent with. The interval’s level is the library’s alpha_ci (0.05 by default); model.reading(0.1) gives the 90% one.

  • Test of k = 0: the likelihood-ratio test that starts do not matter. Here it is overwhelming (p about 1e-55). A large p-value would mean the data cannot tell starts from no effect, and hours alone may do.

  • alpha and beta are the Weibull scale (in equivalent hours) and shape on the combined clock.

The combined age of a unit with 10,000 hours and 400 starts:

model.equivalent(10000, 400)

np.float64(17349.56275956633)

Fitted to hours alone, the same data give a shape of about 1.5, not 2.6: mixing units that wear at different speeds blurs the wear-out, so the hours-only model makes failures look more random than they are.

sp.Weibull.fit(df["hours"], df["c"]).params

array([1.58271676e+04, 1.46435986e+00])

The data: arrays, or a SecondaryClock

fit takes the data as any univariate fit does, on the main clock (x, c, n, and tl or t for late entry), plus x2, the second clock’s reading at each row’s x. x2 is an array, or a SecondaryClock, which also carries the second clock’s name (it becomes the model’s name for the clock) and its readings when units entered observation. The three give the same numbers:

hours, starts, c = df["hours"], df["starts"], df["c"]
by_array = sp.WeibullEquivalence.fit(hours, starts, c=c)
by_clock = sp.WeibullEquivalence.fit(
    hours, sp.SecondaryClock(starts, name="starts"), c=c
)
by_clock.clocks, np.allclose(by_clock.params, model.params)

(('x1', 'starts'), True)

Late entry is given per clock: tl the hours when a unit came under observation, and SecondaryClock(..., tl=...) its starts then. A unit’s entry needs both, and the fit says so if one is missing. Here, units bought second hand, with a fifth of their hours and starts already on them:

entered = sp.WeibullEquivalence.fit(
    hours,
    sp.SecondaryClock(starts, tl=0.2 * starts, name="starts"),
    c=c,
    tl=0.2 * hours,
)
entered.k

18.99774598449531

From a DataFrame, tl_col and tl2_col name the entry columns and x2_name names the second clock (by default its column’s name).

Units inspected rather than watched

A failure found at an inspection happened some time after the previous one: an interval row (c = 2). Give each clock’s reading at both inspections, as N x 2 arrays (equal columns on the rows that are not intervals), or from a DataFrame with xl_col / xr_col and x2l_col / x2r_col. The unit’s combined clock passed its failure age between \(h_a + k s_a\) and \(h_b + k s_b\), so the row contributes \(S(h_a + k s_a) - S(h_b + k s_b)\), whatever the unit did between the two inspections. The same fleet, inspected every 500 hours:

inspect = 500.0
found = df["c"] == 0  # found failed at the first inspection after it
next_inspection = np.ceil(df["hours"] / inspect) * inspect
upper = np.where(found, np.minimum(next_inspection, followed.round()), df["hours"])
lower = np.where(found, np.maximum(upper - inspect, 0.0), df["hours"])
x = np.column_stack([lower, upper])  # hours at the two inspections
x2 = rate[:, None] * x  # starts at the same two inspections
inspected = sp.WeibullEquivalence.fit(
    x, sp.SecondaryClock(x2, name="starts"), c=np.where(found, 2, 1)
)
inspected.k, inspected.param_cb("k")

(18.640945440717356, array([14.41713958, 24.10220453]))

Lives along a duty

The questions that matter are usually about a duty: how long will a peaking unit last? A unit making rate starts per hour ages \(1 + k \cdot rate\) equivalent hours per hour, so its life in hours is the combined life divided by that. The *_at_usage methods answer in hours, with bounds that include the uncertainty in \(k\). The B10 life (the hours by which 10% have failed) of each duty:

rates = np.array([0.01, 0.05, 0.3])
pd.DataFrame(
    {
        "starts per hour": rates,
        "B10 (hours)": model.qf_at_usage(0.1, rates).round(0),
        "lower": model.quantile_cb_at_usage(0.1, rates)[:, 0].round(0),
        "upper": model.quantile_cb_at_usage(0.1, rates)[:, 1].round(0),
    }
)

A peaking unit reaches its B10 life after about 1,900 hours, a base-load unit after about 10,200. The starts made in that time are rate times the hours. And the chance a unit survives 8,000 hours in each duty:

The usual functions (sf, ff, hf, qf, mean and cb) are those of the distribution on the combined clock, in equivalent hours.

The life at one duty, as a plain life model

model.at_usage(rate) binds one rate and gives the life of a unit used at it as an ordinary life model in hours: its sf, ff, df, hf, Hf, qf, random, mean, rmst, cb and quantile_cb take hours only, each the model’s *_at_usage at that rate. rate is in the model’s own units: the second clock’s units per unit of the first, here starts per hour. A unit at that rate ages 1 + k rate equivalent hours per hour (life.acceleration). Hand it to code that expects a univariate model, such as a block of a reliability block diagram (“this pump, peaking”). The model’s unit label goes with it, as typed.

peaking = model.at_usage(0.3)
peaking, peaking.qf(0.1).round(0), peaking.sf(8000).round(3)

(LifeAtUsage(WeibullEquivalence, clocks=('hours', 'starts'), rate=0.3),
 np.float64(1854.0),
 np.float64(0.007))

Its draws are qf(U) for uniform U, so a seed gives common random numbers across models, and its bounds carry the uncertainty in \(k\):

What the model assumes, and its limits

  • Constant usage per unit. Between installation and the time it is seen, each unit is assumed to have used its clocks at a steady ratio (its starts divided by its hours). A unit that ran base load for years and then switched to peaking has the right totals, but the model places its starts evenly over its life. If duties change a lot over a unit’s life, the estimate of \(k\) is an average.

  • The two clocks add. Wear from a start is the same whatever the unit’s age, and does not interact with the running hours.

  • The clocks’ order. \(k\) is measured in units of the first clock. fit(starts, hours) instead gives hours measured in starts, \(k' = 1/k\), with the same fit; choose the order that reads best (“one start is worth k hours”).

  • k on its edge. \(k\) cannot be negative. Where the best fit is \(k = 0\) (starts do not matter), the fit is exactly the distribution fitted to hours alone, the Wald interval on \(k\) does not exist (it is nan, with a warning), and param_cb("k", method="lr"), the profile-likelihood interval, gives one that starts at 0. The test of \(k = 0\) allows for the edge: its p-value is half the usual chi-square one (Self and Liang, 1987).

  • Units with no hours. A unit that failed with starts but no running hours is fine: its age is \(k s\). Such a failure is impossible if starts did not matter, so it rules out \(k = 0\).

  • Data. Univariate data on the main clock, with the second clock read at the same moments: failures (c = 0), units still running (c = 1), units that failed before they were inspected (c = -1), units that failed between two inspections (c = 2, with both clocks’ readings at each), counts n and late entry (tl the main clock’s, SecondaryClock(..., tl=...) the second’s) are taken. Right truncation is not. The constant-usage assumption above is used only for exact failures (it gives the factor below); an interval, a censored unit and a late entry need only the clocks’ readings.

Why the factor (1 + k rate) matters

It is tempting to compute \(T = h + k s\) for each unit and fit a Weibull to the \(T\) values, choosing the \(k\) that fits best. That is wrong. A larger \(k\) stretches every \(T\), and a density on a stretched clock is lower by the stretch, so that likelihood falls as \(k\) grows for a reason that has nothing to do with the data; its best \(k\) is pulled towards 0. The correct likelihood is the one on the hours clock each unit was actually observed on. A unit running at rate starts per hour ages \(1 + k \cdot rate\) times faster than one with no starts, so in hours its failure density is

\[f(h_i + k s_i;\ \theta)\,(1 + k \rho_i), \qquad \rho_i = s_i / h_i ,\]

and a unit still running contributes \(S(h_i + k s_i; \theta)\). The factor \(1 + k\rho_i\) corrects the stretch. This is an accelerated failure time model on hours, with acceleration \(1 + k\rho_i\) (Duchesne and Lawless, 2000), and SurPyval’s tests check that at a fixed \(k\) it is exactly WeibullAFT with the covariate \(\log(1 + k\rho_i)\) and its coefficient fixed at 1. In simulations with \(k = 10\), the naive fit’s estimate collapsed towards 0 while this one’s was unbiased.

The minimum coefficient of variation method of Kordonsky and Gertsbakh (choose \(k\) to make the failures’ \(T\) as alike as possible) is not used: it has no likelihood, so it cannot take units still running, and gives no intervals or tests.
