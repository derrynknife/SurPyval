Recurrent Event Regression Modelling with SurPyval

Modelling recurrent events where we have covariates is simple with surpyval. Using the same API as regular survival regression, all we need to do is select a model and fit it to our data. The two proportional-intensity models are ProportionalIntensityHPP (a constant baseline rate) and ProportionalIntensityNHPP (a time-varying baseline, e.g. Duane or Crow-AMSAA). Both scale a baseline intensity by a covariate factor \(e^{Z\beta}\), so a coefficient \(\beta_k\) multiplies the event rate by \(e^{\beta_k}\) for each unit of covariate \(k\). The theory, assumptions and references are on the Recurrent Event Regression Analysis page; for the models without covariates see Recurrent Event Modelling with SurPyval. When the failures come in several types (failure modes) and a covariate may act on one type and not another, see Several failure modes, each with its own covariate effects. To estimate covariate effects without choosing a baseline shape at all (the Andersen-Gill, Prentice-Williams-Peterson and Wei-Lin-Weissfeld models, with robust standard errors), see Without a baseline shape: Andersen-Gill, Prentice-Williams-Peterson and Wei-Lin-Weissfeld at the end of this page.

Both fitters take the recurrent x / i / c / n arrays exactly as the models without covariates do (including tl / tr truncation and interval-counted rows), plus the covariates Z as the second argument: fit(x, Z, i=..., c=...). Z is either a 2-D array with one row per row of x (repeat an item’s covariates on each of its rows; a 1-D array is one covariate), or a dictionary mapping each item id to its covariate values (a list, or a plain number for a single covariate). The covariates describe the item and must be constant within it: values that change between an item’s rows raise a ValueError (for a load, an environment or an overhaul state that changes during an item’s life, see Covariates that change over time below). Both fitters also take init, the starting values for the search: the baseline parameters on their natural scale followed by one value per coefficient. Gapped observation (windows) is not available with covariates. A covariate column the data cannot determine – a linear combination of the others, or a constant column, whose effect the baseline’s scale already carries (the HPP’s rate, Duane’s b, Crow-AMSAA’s and Cox-Lewis’s alpha) – is aliased, as in every SurPyval regression: its coefficient is nan and listed in model.aliased, one warning names it, and the other parameters and the predictions are those of the fit without it.

Proportional-Intensity HPP

The data are the usual recurrent x / i / c arrays plus a covariate matrix Z with one row per observation. Here three items are each observed until a right-censoring row, and each carries a single covariate (say, a duty cycle) that is constant for the item.

from surpyval.recurrent import ProportionalIntensityHPP
import numpy as np

x = np.array([5.0, 8.0, 6.0, 10.0, 7.0, 9.0])
i = np.array([1, 1, 2, 2, 3, 3])
c = np.array([0, 1, 0, 1, 0, 1])
Z = np.array([[0.1], [0.1], [0.5], [0.5], [0.9], [0.9]])

model = ProportionalIntensityHPP.fit(x, Z, i=i, c=c)

The fit reports the baseline rate parameter and a covariate coefficient. The coefficient enters multiplicatively through \(e^{Z\beta}\), so it reads as the log of the rate ratio: a one-unit increase in the covariate multiplies the event rate by \(e^{\beta}\). (With three events this is only a demonstration of the data format; the worked example below has enough data to learn from.) The same fit with the covariates given per item:

Predicting at a covariate setting

To predict the expected number of events for an item, pass its covariates to cif. The instantaneous rate at a covariate setting comes from iif:

Z_item = np.array([0.5])
print("expected events by t=12 :", round(float(model.cif(12.0, Z_item)), 3))
print("event rate at t=12      :", round(float(model.iif(12.0, Z_item)), 3))

expected events by t=12 : 1.335
event rate at t=12      : 0.111

Because the covariate factor multiplies the whole cumulative intensity, the ratio of expected counts between two covariate settings is constant in time and equals \(e^{(Z_2 - Z_1)\beta}\):

z1, z2 = np.array([0.2]), np.array([0.7])
ratio = model.cif(10.0, z2) / model.cif(10.0, z1)
print("count ratio  :", round(float(ratio), 3))
print("exp((z2-z1)b):", round(float(np.exp((z2 - z1) @ model.coeffs)), 3))

count ratio  : 0.929
exp((z2-z1)b): 0.929

A worked example with known effects

To see what the models can recover, let’s simulate a fleet of 30 electric motors whose failure rate depends on two covariates: whether the motor works in a humid environment (0 or 1) and its duty cycle (between 0 and 1). The true model is a proportional-intensity power law,

\[\Lambda(t \mid Z) = \left(\frac{t}{25}\right)^{1.5} e^{0.7\,\text{humid} + 1.0\,\text{duty}},\]

so the motors wear out (the shape 1.5 is above one), a humid environment multiplies the failure rate by \(e^{0.7} \approx 2\), and full duty multiplies it by \(e^{1.0} \approx 2.7\). The motors entered service at different times, so each is observed for between 30 and 60 months. For a Poisson process the simulation is simple: draw the number of failures from a Poisson distribution with mean \(\Lambda(T \mid Z)\), then place them independently with distribution function \(\Lambda(t)/\Lambda(T)\), which for a power law means \(t = T\,U^{1/1.5}\) for uniform \(U\):

rng = np.random.default_rng(1)
x, i, c, Z = [], [], [], []
for motor in range(1, 31):
    T = rng.uniform(30, 60)                               # months observed
    z = np.array([rng.integers(0, 2), rng.uniform(0, 1)])  # humid, duty
    expected = (T / 25) ** 1.5 * np.exp(z @ [0.7, 1.0])
    k = rng.poisson(expected)
    times = np.sort(T * rng.uniform(size=k) ** (1 / 1.5))
    x += [*times, T]                     # the failures, then the censoring row
    i += [motor] * (k + 1)
    c += [0] * k + [1]
    Z += [z] * (k + 1)                   # the motor's covariates on every row
x, i, c, Z = map(np.array, (x, i, c, Z))
print(f"{(c == 0).sum()} failures on {len(np.unique(i))} motors")

180 failures on 30 motors

Rate ratios and their uncertainty

The fitted model carries the usual likelihood inference. parameter_names lists the baseline parameters followed by the coefficients, standard_errors gives a standard error for each, and param_cb a confidence interval. Exponentiating a coefficient, and the ends of its interval, gives the rate ratio and its confidence interval:

print("parameters :", fleet_hpp.parameter_names)
print("std errors :", fleet_hpp.standard_errors().round(3))
for k, name in enumerate(["humid", "duty"]):
    lower, upper = np.exp(fleet_hpp.param_cb(f"coef_{k}"))
    print(f"{name:6s} rate ratio {np.exp(fleet_hpp.coeffs[k]):.2f}"
          f"  (95% CI {lower:.2f} to {upper:.2f})")

Proportional-Intensity NHPP

When the baseline rate itself varies with time — reliability growth, wear-out — use ProportionalIntensityNHPP with a counting-process baseline. The default baseline is the Duane model; any NHPP baseline (CrowAMSAA, CoxLewis) can be supplied via baseline.

from surpyval.recurrent import ProportionalIntensityNHPP, Duane
import numpy as np

x_toy = np.array([2.0, 5.0, 3.0, 7.0, 1.0, 4.0, 2.0, 6.0])
i_toy = np.array([1, 1, 2, 2, 3, 3, 4, 4])
c_toy = np.array([0, 1, 0, 1, 0, 1, 0, 1])
Z_toy = np.array([[0.2], [0.2], [0.5], [0.5], [0.8], [0.8], [0.3], [0.3]])

toy = ProportionalIntensityNHPP.fit(x_toy, Z_toy, i=i_toy, c=c_toy, baseline=Duane)

Prediction and simulation

Every prediction takes the covariates of the item being predicted as its second argument: cif (the expected number of events), iif (the event rate), inv_cif (the time by which a given number of events is expected) and cif_cb (confidence bounds on the expected number). For a humid motor at half duty:

z = np.array([1.0, 0.5])
print("expected failures by 40 months :", fleet.cif(40, z).round(2))
print("failure rate at 40 months      :", fleet.iif(40, z).round(3))
print("time of the 5th failure        :", fleet.inv_cif(5, z).round(1))
print("95% bounds on the expected count at 20 and 40 months:")
print(fleet.cif_cb([20, 40], z).round(2))

The model can also simulate items with given covariates. mcf(x, Z) estimates the MCF by simulation (which, for these Poisson models, reproduces cif up to simulation noise), and time_terminated_simulation(T, Z, items), count_terminated_simulation(events, Z, items) and their ..._data versions work as for the models without covariates. Their Z is one item’s covariate vector, so a missing (nan) value in it raises a ValueError (see Missing values):

print("closed-form cif :", fleet.cif(np.array([20, 40]), z).round(3))

sims = fleet.time_terminated_simulation_data(40, z, items=5, random_state=2)

As for any Poisson process, the actual number of failures in a future period is Poisson distributed about the expected number, so a plug-in prediction interval for one motor’s failures between 40 and 50 months follows from the fitted cif:

from scipy.stats import poisson

expected = float(fleet.cif(50, z) - fleet.cif(40, z))
print(f"expected {expected:.2f}; 90% prediction interval",
      poisson.ppf([0.05, 0.95], expected))

expected 2.53; 90% prediction interval [0. 5.]

Saving and loading a regression model

Like the other recurrence models, a fitted proportional-intensity model can be saved with to_dict / to_json and restored with surpyval.from_dict / surpyval.from_json. The baseline, its parameters and the coefficients are stored, so predictions are reproduced exactly, and so is the parameter covariance, so the restored model gives the same standard errors, summary() and Wald bounds (cif_cb, iif_cb, cb_tvc). The fitted data and likelihood are not stored, so re-fit for the likelihood (aic()) or the diagnostics.

import surpyval

restored = surpyval.from_dict(fleet.to_dict())
print(np.allclose(restored.cif(40, z), fleet.cif(40, z)))
print(np.allclose(restored.cif_cb(40, z), fleet.cif_cb(40, z)))

True
True

Model checking

The regression models carry the same diagnostics as the unconditional intensity models, applied per item with each item’s intensity scaled by its covariate factor:

print("residual mean :", round(fleet.residuals().mean(), 3))
print("trend         :", fleet.trend_test().trend)

residual mean : 0.836
trend         : increasing

The residuals are the time-rescaling residuals pooled across items (i.i.d. Exp(1) under a well-specified model); the trend test checks whether a time-varying baseline was warranted at all. Here the residual mean is below one although the model is correct: each motor’s final, censored gap is left out of the residuals, and with about six failures per motor that selection is noticeable (see Recurrent Event Regression Analysis). The trend test, unsurprisingly, points to an increasing rate:

fleet.trend_test()

The martingale residuals — observed minus expected failures, one per motor — check the covariate model. If the effect of duty cycle were not log-linear, their average would drift with duty cycle; here there is no obvious pattern:

martingale = fleet.residuals(kind="martingale")
duty = np.array([Z[i == k][0, 1] for k in np.unique(i)])
for label, mask in [("duty < 0.5 ", duty < 0.5), ("duty >= 0.5", duty >= 0.5)]:
    print(label, "mean martingale residual:", martingale[mask].mean().round(2))

duty < 0.5  mean martingale residual: -0.31

A Cramér–von Mises goodness-of-fit test is also available via cramer_von_mises. It is a parametric bootstrap that refits the whole regression for each replicate, so keep n_boot modest while exploring. It tells the two models of the motors apart:

p_hpp = fleet_hpp.cramer_von_mises(n_boot=30, random_state=1).p_value
p_nhpp = fleet.cramer_von_mises(n_boot=30, random_state=1).p_value
print("PI-HPP  p-value:", round(p_hpp, 3))
print("PI-NHPP p-value:", round(p_nhpp, 3))

PI-HPP  p-value: 0.032
PI-NHPP p-value: 0.29

The constant-rate model is rejected at the 5% level, while the power-law model is consistent with the data.

Covariates that change over time

Everything above describes an item by covariates that never change: this motor is in a humid room, that one runs at half duty. Many of the things that drive failures are not like that. A pump runs at high load in some months and low load in others. A machine is overhauled part of the way through its life. A vehicle moves from a sealed road to a gravel one. The covariate belongs to a period of the item’s life, not to the item.

There are two tempting shortcuts, and both give the wrong answer:

  • Use the first (or the last) value. A pump that started on low load and spent most of its life on high load is then filed under “low load”, and the failures that the high load caused are blamed on low load. The effect of the covariate is diluted towards zero, or even reversed.

  • Use the average. A pump that was on high load for half of its life is given a load of 0.5. That throws away when the failures happened. If eight of its ten failures fell in the high-load months, that is strong evidence about load; the average cannot see it. An average is also the wrong arithmetic: the model multiplies the failure rate by a factor, and the average of a factor over time is not the factor at the average. And when the failure rate itself changes with age, a spell of high load late in life costs more failures than the same spell early in life, which no single number per pump can express.

The model for a changing covariate is a small step from the one above. It assumes that the value the covariate has now multiplies the failure rate now: while the pump is on high load its failure rate is the baseline rate at its present age times \(e^{\beta}\), and the moment it returns to low load the rate returns to the baseline. There is no memory: the model does not carry damage from past high-load spells into later low-load ones. (If you believe that past exposure matters, put it in the data as a covariate of its own, such as the cumulative hours at high load so far.) The covariates must be piecewise constant: each holds one value over an interval of time and then steps to another. The theory is on the Recurrent Event Regression Analysis page.

Fitting uses the same names and data shapes as the time-varying fits of the life models (fit_tvc, fit_tvc_timeline and their _from_df forms; see Regression Modelling with SurPyval), so what you know from one carries over to the other.

The data: a log of what happened and when

To have a known answer to recover, we simulate 40 pumps, each watched for three to five years. Two things change over a pump’s life. Its load switches between low and high a few times, and high load multiplies the failure rate by \(e^{0.8} \approx 2.2\). Most pumps are overhauled once, somewhere between months 12 and 48, and from then on fail at \(e^{-0.6} \approx 0.55\) of the rate they otherwise would. Underneath, every pump wears out: with both covariates at zero the expected number of failures by month \(t\) is \((t / 20)^{1.4}\).

The natural record of such a history is a timeline: one row each time something happens to a pump, saying when it happened, whether it was a failure (c = 0) or not (c = 1), and what the covariates are from that moment on:

import pandas as pd

rng = np.random.default_rng(1)
true_coefficients = np.array([0.8, -0.6])       # high load, overhauled

def baseline(t):                 # expected failures by month t at Z = 0
    return (t / 20.0) ** 1.4

def baseline_inverse(m):
    return 20.0 * m ** (1 / 1.4)

rows = []
for pump in range(1, 41):
    end = rng.uniform(36, 60)                   # months watched
    switches = rng.uniform(0, end, rng.integers(1, 5))
    overhaul = rng.uniform(12, 48) if rng.uniform() < 0.8 else np.inf
    edges = np.unique(np.r_[0.0, switches, min(overhaul, end), end])
    high = bool(rng.integers(0, 2))             # the load it starts on
    for a, b in zip(edges[:-1], edges[1:]):
        z = np.array([float(high), float(a >= overhaul)])
        expected = (baseline(b) - baseline(a)) * np.exp(z @ true_coefficients)
        fails = baseline_inverse(
            rng.uniform(baseline(a), baseline(b), rng.poisson(expected))
        )
        rows.append((pump, a, 1, *z))           # the covariates from a on
        rows += [(pump, t, 0, *z) for t in fails]
        if b in switches:
            high = not high                     # the load changes at b
    rows.append((pump, end, 1, *z))             # the end of the record
pump_log = pd.DataFrame(
    rows, columns=["pump", "month", "c", "high_load", "overhauled"]
).sort_values(["pump", "month"], ignore_index=True)
print(f"{(pump_log.c == 0).sum()} failures on {pump_log.pump.nunique()} pumps")
pump_log[pump_log.pump == 1].round(2)

A few rules of the start-stop form, all shared with the life models:

  • An item’s intervals must not overlap. They may leave gaps: the item is simply not counted as at risk during a gap (it was out of service, or nobody was recording). A first interval that starts after zero is delayed entry: the item is only watched from then on.

  • Cutting an interval in two at any point, with the same covariates on both pieces, changes nothing. So there is no harm in cutting at every calendar month if that is how the data arrive.

  • Where failures are only counted per period (so many failures between two inspections) rather than timed, give the period as one row with c = 2 and the count in n. This is the same meaning c = 2 and n have for the fixed-covariate fit.

  • A missing covariate value is refused: the row is part of an item’s history, and dropping it would silently remove the item from risk for that interval (see Missing values).

Left-censored counts (c = -1) and right truncation (tr) are not part of the start-stop form: a count goes in as a c = 2 row over its interval, and a fit that needs tr is refused rather than approximated.

What carries over, and what does not yet

A model fitted this way is an ordinary proportional-intensity model. The fixed-covariate predictions (cif, iif, inv_cif, cif_cb, iif_cb) answer for an item held at one covariate setting for its whole life; summary, standard_errors, param_cb, covariance, aic and bic work as before; simulation and mcf simulate an item at one fixed covariate vector; and to_dict / from_dict keep every prediction, the ones along a schedule included.

Some things are not available for a model fitted to changing covariates, and each refuses with a message that says so, instead of quietly treating the covariates as fixed:

  • residuals, cramer_von_mises, trend_test, diagnose and plot read each item’s single covariate row, which such a fit does not have.

  • Simulation along a schedule: the simulation methods and mcf take one covariate vector, and refuse a schedule. Use cif_tvc for the expected count along a schedule.

  • A covariate that changes continuously (a CovariatePath) is refused by the three _tvc methods; approximate it by steps.

  • fit_penalised has no time-varying form, and the _from_df forms take Z_cols only (no formula), as this model’s fit_from_df does.

Several failure modes, each with its own covariate effects

A repairable item rarely fails in only one way. A pump has seal failures and electrical trips; a vehicle has brake, tyre and engine repairs; a patient is readmitted for different reasons. Recurrent Event Modelling with SurPyval shows how CauseSpecificNHPP fits one failure-rate curve per failure mode (event type). This section adds covariates to that picture.

The question it answers is: which covariate drives which kind of failure? Abrasive fluid wears seals; there is no reason for it to trip the motor’s protection. A weak power supply causes trips and does nothing to the seal. The model gives every failure mode

  • its own baseline: how often that kind of failure happens, and how that changes with age, on an item whose covariates are all zero; and

  • its own coefficients: one per covariate, saying by what factor the covariate multiplies the rate of that kind of failure.

So “abrasive service triples seal failures and leaves the trips alone” is something the model can say, and can say with confidence bounds on each part.

Reading a rate ratio per mode. The exponential of a coefficient is a rate ratio: the factor by which one more unit of the covariate multiplies the rate of that mode’s failures, at every age. A rate ratio of 3 for abrasive on the seal mode means that, of two pumps of the same age, the one in abrasive service is having seal failures three times as often. A rate ratio of 1 means the covariate does nothing to that mode; below 1, it protects against it. Each mode has its own ratio for each covariate, with its own interval. An interval that contains 1 says the data do not show an effect on that mode. It does not say there is none: a mode with few failures has wide intervals.

Why not fit all the failures together? Because a covariate that matters a great deal for one mode can look unimportant, or vanish, in the total. If seal failures are a small share of all failures, tripling them moves the total rate only a little, and a model of all failures reports a small rate ratio that may not even be distinguishable from 1. The conclusion “abrasive service hardly matters” would be wrong where it counts: for the seals, for the spare seals to hold, and for the decision whether a better seal is worth buying. A covariate that raises one mode and lowers another can cancel altogether. Fitting the modes apart keeps each effect at full strength, and adding the modes back up (the totals below) still gives the answer for failures of any kind.

What the model assumes. The failures of each mode arrive as a Poisson process (a repair leaves the item as it was just before the failure, as in the models above), and the modes do not interfere with each other: a seal failure neither brings a trip forward nor postpones it. Under that assumption the modes can be fitted one at a time, each to its own failures over the whole time every item was watched, with the other modes’ failures simply left out. That is what CauseSpecificProportionalIntensity does: each mode is an ordinary proportional-intensity fit (the models at the top of this page), and the fitted models are in models[event]. The formulas are on the Recurrent Event Regression Analysis page.

The data

To have a known answer, we simulate 60 pumps watched for 48 months. Half pump an abrasive slurry. Seal failures are the rarer mode; they become more frequent as a pump ages, and abrasive service triples them (a coefficient of 1.1). Electrical trips are the common nuisance: about one every four months, at a constant rate, whatever the fluid (a coefficient of 0). All modes together: the totals

Some things the single-mode models and CauseSpecificNHPP offer are not carried over to this model yet. Each of these refuses with a message that says what to use instead:

  • Diagnostics (diagnose, residuals, cramer_von_mises, trend_test) and plot: call them on one mode’s own model, modes.models["seal"].diagnose(). Each mode is a Poisson process of its own, so its diagnostics are valid there (for a fixed-covariate fit; a mode fitted to changing covariates refuses them, as above).

  • Simulation and the simulated mcf: simulate each mode from its own model at a covariate row; the modes are independent, so their simulated failures can be pooled. The expected counts need no simulation (cif, total_cif).

  • Forecasts (forecast and surpyval.forecast): the expected number of failures over a time ahead is total_cif_tvc(age + horizon, Z, xl=[age], given=age), with bounds from total_cb_tvc; one mode’s forecast with its prediction interval is surpyval.forecast( modes.models["seal"], age, horizon, Z=Z).

  • growth, and the MTBF methods (mtbf, total_mtbf and their bounds): read each mode’s trend parameter from summary(), and take the reciprocal of iif / total_iif and of their bounds.

  • Counts of failures between inspections (c = 2) and right truncation: a count carries no mode per failure. Fit each mode’s own counts with the single-mode regression.

  • Only the Wald (delta-method) bounds are offered, as on the single-mode models; there is no penalised fit, and the _from_df forms take Z_cols only (no formula).

Without a baseline shape: Andersen-Gill, Prentice-Williams-Peterson and Wei-Lin-Weissfeld

Every model above gives the baseline intensity a formula. Three fitters leave it unspecified, as CoxPH does for a single event, and estimate only how the covariates change the rate: AndersenGill, PrenticeWilliamsPeterson and WeiLinWeissfeld. They differ in what they assume a repeat event is; Recurrent Event Regression Analysis sets the four models side by side, in words. In one line each:

  • AndersenGill: an event does not change the item; one baseline for all events. The coefficient is a log rate ratio.

  • PrenticeWilliamsPeterson: each event number has its own baseline, and an item is at risk of its second event only after its first. time_scale="total" (the default) measures time as the item’s age, time_scale="gap" as the time since its last event.

  • WeiLinWeissfeld: the time from the start to the first event, to the second, and so on, each modelled on its own.

All three take the event log the other recurrent models take: fit(x, Z, i=..., c=...), with c = 0 for an event and c = 1 for the end of an item’s observation, or fit_from_df with the column names. All three return the same kind of model, and all three report robust standard errors, with each item a cluster: an item’s events are not independent pieces of evidence, and the robust errors do not pretend they are.

The data are laid out for the model (the risk interval of each row, and its event number) and handed to CoxPH, so tied times, a coefficient the data cannot determine and a likelihood with no maximum are handled, and reported, as CoxPH does. The results equal R’s coxph(... + cluster(id)) on the matching layout.

An engineering example: trucks, and what the log does not record

Eighty haul trucks are watched for 36 months; half work a dusty pit. To have a known answer the breakdowns are simulated: dust multiplies the breakdown rate by \(e^{0.5} \approx 1.65\), and, as in any real fleet, some trucks are simply worse than others for reasons the log does not record (a factor hidden that the analysis never sees).

import numpy as np
import pandas as pd
from surpyval.recurrent import AndersenGill

rng = np.random.default_rng(2026)
months = 36.0
rows = []
for truck in range(80):
    dusty = float(truck % 2)
    hidden = rng.gamma(1 / 0.6, 0.6)   # not in the log
    expected = (months / 9.0) ** 1.3 * hidden * np.exp(0.5 * dusty)

    rows += [(truck, t, 0, dusty) for t in np.sort(times)]
    rows.append((truck, months, 1, dusty))
fleet_log = pd.DataFrame(rows, columns=["truck", "month", "c", "dusty"])

ag = AndersenGill.fit_from_df(

)

A medical example: one trial, three questions

Three hundred patients are randomised to a treatment or not, and followed for 24 months for recurrent infections. In this simulation an infection changes the patient: the first comes slowly (on average after 30 months untreated), and after one, the next comes much sooner (8 months). The treatment stretches every one of these waiting times by the same factor, \(e^{0.5}\), a log hazard ratio of \(-0.5\) for each wait.

from surpyval.recurrent import PrenticeWilliamsPeterson, WeiLinWeissfeld

rng = np.random.default_rng(1989)
follow_up = 24.0
rows = []
for patient in range(300):
    treated = float(patient % 2)
    age, number = 0.0, 1
    while True:
        mean_wait = (30.0 if number == 1 else 8.0) * np.exp(0.5 * treated)
        age += rng.exponential(mean_wait)
        if age >= follow_up:
            break
        rows.append((patient, age, 0, treated))
        number += 1
    rows.append((patient, follow_up, 1, treated))
trial = pd.DataFrame(rows, columns=["patient", "month", "c", "treated"])

columns = dict(x_col="month", Z_cols="treated", i_col="patient", c_col="c")
fits = {
    "Andersen-Gill": AndersenGill.fit_from_df(trial, **columns),
    "PWP, gap time": PrenticeWilliamsPeterson.fit_from_df(
        trial, time_scale="gap", max_events=3, **columns
    ),
    "PWP, total time": PrenticeWilliamsPeterson.fit_from_df(
        trial, max_events=3, **columns
    ),
    "Wei-Lin-Weissfeld": WeiLinWeissfeld.fit_from_df(
        trial, max_events=3, **columns
    ),
}

All four find that the treatment helps, and they are answers to different questions:

  • The gap-time model matches how these data arise, and recovers the effect on each wait (the true value is \(-0.5\)). Its robust and naive standard errors agree: once each infection number has its own baseline, nothing is left over to make a patient’s waits alike.

  • The Andersen-Gill coefficient is the effect on the overall infection rate. It is larger in size, because the treatment helps twice: it delays each infection, and by delaying the first it keeps patients longer in the state where infections are rare. Its robust error is well above its naive one: with a single baseline, the dependence the model leaves out (a patient who has had one infection is on the fast clock) shows up as patients differing.

  • The Wei-Lin-Weissfeld coefficient is the effect on the time from randomisation to each infection number. It too carries the knock-on effect of delaying earlier infections, and is the one that compares the groups as randomised.

max_events=3 models the first three infections only: few patients have a fourth, and a baseline estimated from a handful of them is poorly determined. For the conditional models, what follows a patient’s third infection is left out; for the marginal model it is the number of event numbers modelled.

With a baseline per event number, cif takes the event number as stratum, and for the gap-time and marginal models sf turns it into a probability: of waiting longer than x for that infection, or of not having had it by x months after randomisation.

Start-stop rows, saving, and what is not available

In an event log, the covariates on a row are those in force up to that row’s time, so they may change from one of an item’s rows to the next (the marginal model, which starts every clock at 0, needs them constant within an item and refuses otherwise). For an item that enters late, a break in its observation, or a covariate that changes between events, AndersenGill and PrenticeWilliamsPeterson take start-stop rows, fit_tvc(i, xl, xr, c, Z) or fit_tvc_from_df: each row an interval (xl, xr] of one item, ending in an event (c = 0) or not. model.cox is the Cox model fitted to the laid-out rows, for anything this model does not wrap: model.diagnose() is its diagnose() (the proportional-hazards tests, read here as a screen, since they take the rows as independent), and its residuals are row by row. Not available yet, each a refusal or an absent method rather than a wrong answer:

  • Bounds on the curve (cif_cb): the robust variance is of the coefficients only. model.cox.cb(x, Z, on="Hf") gives the model-based bound.

  • Simulation and forecasts: the baseline has no shape beyond the data. Use the parametric models above.

  • Counted failures (c = 2) and left-censored rows: the partial likelihood needs each event’s time. ProportionalIntensityNHPP takes them.

  • Weights and penalised fits.

  • Several failure modes: fit one model per mode, to that mode’s events with the other modes’ rows flagged c = 1 (as CauseSpecificProportionalIntensity does for the parametric models).

Recurrent events that end in a terminal event

The models above take the end of an item’s observation as uninformative. When the history ends in an event that depends on the recurrences – a unit scrapped after too many repairs, a patient who dies after repeated admissions – JointFrailty models the two kinds of event together: each item has one unobserved frailty that raises its rate of recurrences and its hazard of the terminal event (the theory is on Recurrent Event Regression Analysis).

The rows are those of the other recurrent models – each event at its age (c = 0), and one row per item closing its observation (c = 1) – plus a flag terminal, 1 on the closing row where the terminal event closed it and 0 where observation simply stopped.
